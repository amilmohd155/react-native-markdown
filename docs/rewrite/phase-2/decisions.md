# Phase 2 · Implementation decisions

These are decisions made while building Phase 2, numbered `P2-n`. Design-level decisions (`D1`–`D8`) live in the [roadmap decision log](../07-roadmap.md#decisions); Phase 1's are `P1-n` in [../phase-1/decisions.md](../phase-1/decisions.md). A P2 decision that changes the design must also update the design doc it affects.

**Status values:** `Proposed` (awaiting agreement), `Accepted`, `Superseded by P2-n`.

## Template

```md
## P2-n: Title
- **Status:** Proposed | Accepted | Superseded by P2-x
- **Date:** YYYY-MM-DD
- **Context:** what forced the decision (link evidence)
- **Decision:** what we do
- **Consequences:** what changes, what it costs, which docs were updated
```

## P2-1: Exit criterion wording and the F4 fixture

- **Status:** **Accepted (2026-11-06)**, with a redefined bar and a recorded waiver (below). The iPhone and `F4c` re-check is waived by [P2-8](#p2-8-iphone-run-and-f4c-deferred). Earlier status, kept for the record: the bars hold on the web simulation at the 50 ms window, but fail on the S25 FE `core` at 50 ms (`F4a` 6.30× / 7.11× against 5×; `F4b` 2.46× / 2.51× against 2×), because of footnote-triggered full re-parses (below).
- **Date:** 2026-11-05
- **Context:** The roadmap says "streaming a 10 KB message costs under 2× a single full parse in total". It does not say how many chunks or when they arrive. A throwaway check gave tail re-parse 10.4× at 500 chunks and 2.0× at 50 chunks. S0 re-measured with the real parser and converter ([results](../02-benchmarks.md#phase-2-streaming-spike-s0)): at 20-character chunks the tail re-parse costs 10.7× with frame coalescing and 11.3× with no window, and a flush has a per-flush floor, so cheaper work alone does not reach 2×. Only a long flush window does: 200 ms gives 1.84× at about 96 ms mean lag, which is too visible. At 195-character chunks every window up to 100 ms stays at 2.0 to 2.2×.
- **Decision (original wording, 2026-11-05; superseded in part by the accepted bar and waiver below):** the criterion is `streamCost`: total flush cost with the default coalescing window ([P2-4](#p2-4-coalescing-policy); the bars are stated for an explicit 50 ms window; see the accepted bar below), as a multiple of one full `parse()` of the same text. It must be at most **2×** on `F4b` (50 chunks of about 195 characters, 16 ms paced) and at most **5×** on `F4a` (500 chunks of about 20 characters). The original "2× on a 500-chunk stream" is waived for the 20-character case. `F4c` (a real transcript) is re-checked at S5, and the bar is re-confirmed or revised then. The 5× figure assumes the 50 ms window, so it moves if P2-4 changes the window.
- **Web evidence (2026-11-06; [results](../02-benchmarks.md#phase-2-web-benchmark-s5-web-part)):** headless Chrome 156, 4× CPU throttle, Apple M1, SHA `f056677`, 5 warm-up and 20 measured runs, `bench/stream-web.mjs` (simulated arrival at one chunk per 16 ms; the conversion is included, the splice and React commit are not; `F4c` skipped, synthetic transcripts only). `streamCost` p50 / p90:
  - **50 ms window (the window the bars assume):** `F4a` 4.28× / 4.80× against the 5× bar (a pass in the web simulation only, with a thin p90 margin, and not the accepted figures; see below); `F4b` 1.42× / 1.59× against 2× (a pass in the web simulation only).
  - **No window or a 16 ms frame:** `F4a` 11.3× and `F4b` 2.12× (both fail). Naive re-parse is 246.8× and 25.95×.
  - So the bars hold on the web **only at the 50 ms window**, not per chunk or per frame. That is the reading of this criterion that was already expected from S0; the web run confirms it with the full method, and does not extend to the S25 FE or an iPhone.
  - **`F4d` bar, accepted (2026-11-06): an absolute one, not a ratio.** One full parse of the code-heavy text is 1.9 to 3.5 ms on the S25 FE (about 0.1 ms on the web, near Chrome's timer granularity), so its ratios are noise. **Accepted: total flush cost at most 20 ms over the stream at the 50 ms window, on the S25 FE (Hermes release).** The `core` measured 15.5 ms (p90 15.7) with the open-fence fast path and 26.6 ms (p90 33.3) without it ([device results](../02-benchmarks.md#phase-2-device-benchmark-s5-s25-fe)); 20 ms is about 1.3× the with-fast-path p90 and sits below the without-fast-path figure. The fast path ([P2-5](#p2-5-open-fence-fast-path)) is worth keeping: it nearly halves `F4d` (26.6 to 15.5 ms at p50). Accepted with the rest of this decision (2026-11-06): the `core` 15.5 ms (p90 15.7) with the fast path meets it. The web run measured 5.6 ms (p90 6.8) at the 50 ms window on `F4d`. The looser 40 ms figure (the device `sim` harness, 38.3 ms at the 50 ms window) is noted only; it is **non-gating**.
  - **Device evidence (2026-11-06, S25 FE, SM-S731B, Android 17, Hermes release, New Architecture, 120 Hz pinned; [results](../02-benchmarks.md#phase-2-device-benchmark-s5-s25-fe)):** same SHA and method (5 warm-up, 20 measured, p50 / p90), two harnesses. `sim` is the web run's code (tail parse and conversion, no splice, no full re-parse): `F4a` 3.48× / 3.72×, `F4b` 1.32× / 1.39× at 50 ms, a pass, as on the web. **`core`** (the real `createMarkdownStreamCoreWith`: parse, splice, full-reparse triggers, `done()`): **`F4a` 6.30× / 7.11×, `F4b` 2.46× / 2.51× at 50 ms, a fail on both bars.** No window: `F4a` 15.6× / 16.1×, `F4b` 3.21× / 3.39×.
  - **Cause: full re-parses.** F2 ends in a footnote definition. While it streams, each flush that contains it re-tokenizes the whole source ([P2-3](#p2-3-parsefrom-contract)): 5 full re-parses per `F4a` stream at 20-character chunks, 3 at 33 ms, 2 at 50 ms, 1 at 100 ms and 200 ms, and 1 on `F4b`; about 17 ms each. Without the two at 50 ms, the `F4a` total would be about 74 ms (107.0 minus 2 × about 16.5), about 4.6× the 16.2 ms full parse, under the bar (an estimate from the counts, not a run with the trigger off; the footnote-free variant `R` later measured 4.32×, see below).
  - **Options, resolved (2026-11-06):** (a) make an open footnote tail cost a tail parse: tried and dropped, see the [P2-3 note](#p2-3-parsefrom-contract); (b) redefine the bar to exclude the footnote-triggered full re-parse: **chosen**, together with (c) a waiver for streams that end in a footnote definition: **chosen** (accepted wording below).
  - **Accepted bar (2026-11-06).** The `streamCost` bars (`F4a` at most 5×, `F4b` at most 2×, at the 50 ms default window, as a multiple of one full `parse()` of the same text) apply to the **steady-state flush cost**: the total measured through the real core, **excluding the necessary full re-parse that the first appearance of a footnote definition triggers**. The footnote full re-parses are not hidden: their count and cost are reported explicitly next to every `streamCost` figure (on the S25 FE at 50 ms: 2 per `F4a` stream and 1 on `F4b`, about 17 ms each, against a full parse of 16.2 ms).
  - **Honest reading of the device data** (`bench/results/stream-device-s25fe-release-2026-11-06.json`, S25 FE, Hermes release, `core`, 50 ms): `F4a` is **6.30× / 7.11×** (p50 / p90) with 2 full re-parses. Excluding both re-parses it would be about 4.6× (an estimate: 107.0 ms minus 2 × about 16.5 ms, over the 16.2 ms full parse; not a measurement with the trigger turned off). Excluding **only the one necessary re-parse** it would be about 5.6× (107.0 minus about 16.5, over 16.2; the same kind of estimate), which **still misses** 5×. The redefinition alone therefore does not make `F4a` pass, so a waiver is also needed. `F4b` excluding its one re-parse was estimated at about 1.5x ((40.1 − 16.4)/16.26), under 2x; the footnote-free measurement is **1.42× / 1.44×** (variant `R`, see the footnote-free result below). The waiver is needed for `F4a` only, and `F4b` is waived for consistency. In this decision, the necessary full re-parse is the first flush in which the footnote definition appears.
  - **Accepted waiver.** The `F4a` 5× bar and the `F4b` 2× bar are **waived for documents that end in a footnote definition** (F2 does), because the open footnote definition forces a full re-parse on each flush that contains it ([P2-3](#p2-3-parsefrom-contract)). The accepted figures for F2 on the S25 FE at 50 ms are the measured ones: **`F4a` 6.30× / 7.11×** and **`F4b` 2.46× / 2.51×** (p50 / p90), recorded as accepted, not as passes. The web simulation (`F4a` 4.28× / 4.80×, `F4b` 1.42× / 1.59×) and the device `sim` harness (3.48× / 3.72×, 1.32× / 1.39×) leave out the full re-parses and are not the accepted figures.
  - **Footnote-free variant required.** A footnote-free fixture variant is held to the **original** bars (`F4a` at most 5×, `F4b` at most 2× at the 50 ms window, through the real core). The device data has no such variant: it holds only `F4a`, `F4b` and `F4d` (F2 and the code-heavy text), `F4c` was skipped, and `F4d` is judged by its own absolute bar, not as a stand-in. **Result (2026-11-06, S25 FE, `core`, 50 ms window; [results](../02-benchmarks.md#footnote-free-variant-s25-fe)):** two footnote-free F2 variants, held to the original bars, both pass. `R` (the footnote reference and the definition line removed) is `F4a` **4.32× / 4.34×** and `F4b` **1.42× / 1.44×** (p50 / p90); `P` (the definition line kept as a plain paragraph) is `F4a` 4.28× / 4.40× and `F4b` 1.42× / 1.45×; the control (`orig`) reproduced the waived figures, 6.26× / 6.36× and 2.43× / 2.47×. `R` and `P` have 0 full re-parses (`orig`: 2 on `F4a`, 1 on `F4b`). The waiver is therefore confirmed to be exactly the footnote cost, about 1.45× on `F4a` at 50 ms (6.26 / 4.32), and **this decision is not reopened**. The bars hold only at the 50 ms window: with no window `F4a` is still about 10.6× (`R`). The run was in a steady slow CPU mode (full parse 29.6 ms against 15.9 to 18 ms in the warm-up), the same for every variant, so the ratios are comparable and the absolute milliseconds are not comparable to the earlier run; it did not go through the React hook. **An iPhone run is waived ([P2-8](#p2-8-iphone-run-and-f4c-deferred)).**
  - **Window dependence unchanged.** The bars assume the 50 ms window. At the per-frame default on native the multiple is higher; the accepted figures are for an explicit 50 ms window (see the interplay with [P2-4](#p2-4-coalescing-policy) below).
  - **Interplay with [P2-4](#p2-4-coalescing-policy):** the web default there is a 16 ms window, and native uses a per-frame flush. Both are in the failing rows above. The bars are therefore met only if `flushIntervalMs` is set to about 50 ms, or if S5 re-expresses the criterion for the default schedule (absolute milliseconds, as P2-4 already asks). Resolved by the acceptance above: option (a), the bars at an explicit 50 ms window; the default schedule's absolute cost is reported, not gated. The web run shows the default schedule's total cost is still small (46.7 ms for the whole `F4a` stream, 8.5 ms for `F4b`).
- **Consequences:** if accepted, the waiver is recorded here and in the roadmap, as [P1-25](../phase-1/decisions.md#p1-25-the--5-parse-plus-first-render-exit-criterion-is-waived-for-phase-1) did for Phase 1. The `F4c` transcripts in `bench/fixtures/transcripts/` are synthetic (no API key or recording was available), so they do not set the bar; real ones must be recorded before S5. Splice cost and React commit are not in the S0 numbers; S1 and S5 measure them. Updates `07-roadmap.md`, `06-testing.md`, [benchmark-protocol](./benchmark-protocol.md#f4), [work-breakdown](./work-breakdown.md#why-s0-comes-first) and the checklist in the [README](./README.md#exit-criteria).

## P2-2: Splice strategy

- **Status:** Accepted (2026-11-05). Implemented in S1 (`src/stream/splice.ts`): about 0.105 ms per splice at 900 blocks on Node, [measured](../02-benchmarks.md#s1-stream-core-node-proxy). Re-measure on Hermes at S5; the table is private, so B or C can still replace A.
- **Date:** 2026-11-05
- **Context:** A stream update must produce a new immutable `NodeTable` sharing the closed prefix. Options A (copy), B (shared append buffer), C (chunked): [table-splicing](./table-splicing.md#splice-strategy). S0 did not measure splice cost (the splice does not exist yet), so it gave no evidence that the copy matters; S1 measures it.
- **Decision (proposed):** A (copy the prefix columns per flush), unless S0 shows the copy matters. The table is private, so this is reversible.
- **Consequences:** none on the public API. Updates `03 · Document model` only if the strategy changes the "immutable after build" wording.
- **Note (2026-11-05, S2.5), found by the memo test, not changing the decision above:** the `isSameBlock` prefix fast path ([table-splicing](./table-splicing.md)) never fires through `<Block>`. `Block`'s memo compares the props of its last render with the new ones, so a block's retained table is the one it was last rendered with, from when it was still the open block; `i < stableCount` is then never true for that table, and closed blocks fall back to the source-text comparison. Over a test stream no comparison took the fast path. Rendering is still right (only the open block re-renders) but the saving the splice section claims (about 6 ms per flush at 900 blocks on the S25 FE) is not realized. Deferred to S5: options are to compare against the previous flush's table (preferred), or to track the last verified table per block. `src/api/__tests__/streamMemo.test.tsx` holds an `it.failing` that starts failing once the fast path works, which is the cue to make it a plain `it`.
- **S5 resolution (2026-11-06): the gap is accepted, no code fix.** Measured on the S25 FE (SM-S731B, Android 17, Hermes release, New Architecture, 120 Hz pinned, SHA `f056677`, 12 measured runs per variant and stream; [results](../02-benchmarks.md#issameblock-comparator-s5-s25-fe), `bench/results/isSameBlock-device-s25fe-2026-11-06.json`). The comparator costs 0.151 / 0.389 ms p50 / p90 per flush on the 10 KB stream (58 blocks) and 0.428 / 1.276 ms at 862 blocks (0.703 / 2.381 ms for late flushes). The "about 6 ms per flush at 900 blocks" claim did not reproduce. Total comparator time over the stream is 57.4 ms (p50) of 7,192 ms at 862 blocks (about 0.8%) and 28.0 of 7,851 ms at 58 blocks (about 0.36%). Whole-stream time was unchanged by either spike. Comparator time was measured with `performance.now()` around `blockPropsEqual`, summed per React commit (one commit per flush), in scratch copies (about 0.065 µs timer overhead per call).
  - **Why the naive fix is wrong:** comparing against "the previous flush's table" is unsound (a skipped render or a suspended flush leaves a block compared against a table it never rendered with, and the chain of tables is retained).
  - **Options kept, not merged (uncommitted spike branches, for reference):** A, per-block version stamps in an `Int32Array` (`worktree-agent-acb7d87e6c24cbdcc`, 5 files): 0.211 / 0.337 ms p50 / p90 at 862 blocks. B, a `WeakMap` in `Block.tsx` (`worktree-agent-a91d4c109d9f846dd`, about 16 lines): 0.255 / 0.396 ms. Both save about 0.2 ms per flush: 35.4 ms (A) and 30.4 ms (B) over a stream at 862 blocks, about 0.49% and 0.42% of stream time.
  - **Revisit trigger:** a larger-document or real-transcript (`F4c`) workload where the comparator exceeds about 2 ms p50 per flush. Then take A or B (B is smaller).
  - The `it.failing` in `streamMemo.test.tsx` stays as the record of the accepted gap.
- **Splice and Hermes heap re-measure (2026-11-06, S25 FE, Hermes release; done; [results](../02-benchmarks.md#splice-cost-and-done)):** the splice costs **3.5 / 6.2 ms** (p50 / p90) per `F4a` stream at the 50 ms window (137 splices, **about 0.026 ms per splice**), 0.37 / 0.40 ms on `F4b` (16 splices) and 0.25 / 0.27 ms on `F4d` (38 splices); about 3% of the `F4a` flush cost. Heap: the finished stream retains **+39,166 bytes** over the same document built statically on `F4a` (92,728 against 53,562) and **+13,639 bytes** on `F4d` (32,231 against 18,592), identical in all 20 runs (deterministic). Strategy A stays; nothing to change.

## P2-3: `parseFrom` contract

- **Status:** Accepted (2026-11-05). Implemented in S1 for the markdown-it backend; types in `src/stream/types.ts`.
- **Date:** 2026-11-05
- **Context:** `parseFrom(source, offset, options)` exists on `ParserBackendImpl` without carried context. A tail-only parse loses link references, heading-slug counters and footnote state ([stream-algorithm](./stream-algorithm.md#carried-context)). A native backend (phase 4) must implement the same contract.
- **Decision (proposed):** `parseFrom(source, offset, carried, options) → { table, carried, prefixCarried, newReferences, hasFootnoteDefinition }` (`ParseFromResult`, `src/stream/types.ts`) as in [table-splicing](./table-splicing.md#parsefrom). The carried context is an opaque backend-defined value; the stream core only passes it back. `prefixCarried` seeds the next append, and the two flags drive the full-reparse triggers. The markdown-it backend implements it; with footnotes defined in the prefix it tokenizes the whole source (accepted for S1, revisit at S5).
- **Option A tried and dropped (2026-11-06, S5; the P2-1 choice is [here](#p2-1-exit-criterion-wording-and-the-f4-fixture)).** Option A was "remember the known footnote labels so an open footnote tail does not force a full re-parse". It was implemented test-first in a scratch worktree (8 files, +228/-20): the core remembers known labels, full re-parses at the 50 ms window go from 2 to 1 (per-flush count 5 to 1), and all gates were green (unit 843, stream 1410, spec 1413, web 383, `check:expo-go` OK). But the measured **total flush time did not change on F2**: `F4a` at 50 ms went from 6.4× to 6.4 to 6.6× on Node, and `F4b` from about 3.0× to about 3.1×. Every remaining flush still tokenizes the whole source (Trigger B: the closed block containing `[^perf]` mentions the label), and tokenizing is most of the cost of a full parse. **Dropped, not merged.** The earlier predictions for it (about 5.4× and 4.6× for `F4a` at 50 ms) were wrong for option A; the 4.6× figure is only the estimate for removing the re-parses outright, which A does not do. Patch kept as a recoverable backup outside the repo: `/Users/docren155/.claude/jobs/5bec978c/tmp/optionA-footnote.patch`. **The unbuilt route to a real gain:** carry `{label, count}` from the prefix and seed `env.footnotes` so a tail parse can resolve the references; the block phase sets `refs[':L'] = -1`, which clobbers seeded ids, so that needs care. About 1 to 2 days, deferred. **Revisit trigger:** real transcripts (`F4c`) or users with long documents that end in a footnote showing footnote flushes dominating the stream cost.
- **Note (2026-11-06, S5): the footnote full re-parse is now measured.** On the S25 FE (Hermes release) `core`, F2 ends in a footnote definition, so while it streams every flush that contains it is a full re-parse of about 17 ms (the full parse is 16.2 ms): 5 per `F4a` stream at 20-character chunks, 3 at 33 ms, 2 at 50 ms, 1 at 100 and 200 ms, and 1 on `F4b` ([results](../02-benchmarks.md#phase-2-device-benchmark-s5-s25-fe)). That is about 33 of the 107 ms `F4a` total at 50 ms and is what pushes `streamCost` to 6.30× / 7.11× against the 5× bar of [P2-1](#p2-1-exit-criterion-wording-and-the-f4-fixture). Option A (an open footnote tail costing a tail parse) was tried and dropped, see the note above; P2-1 is accepted with a redefined bar and a waiver. This decision is not changed.
- **Consequences:** updates `03 · Backend interface` and `src/parse/backend.ts`.

## P2-4: Coalescing policy

- **Status:** Accepted (2026-11-05). Implemented in S2 (`src/stream/scheduler.ts`, `src/api/useMarkdownStream.ts`) and measured in Node, on the S25 FE (Hermes release) and on the web ([results](../02-benchmarks.md#phase-2-scheduler-s2)). iOS, native background behaviour and a real LLM transcript (F4c) are not measured; they are S5 items.
- **Date:** 2026-11-05
- **Context:** 05 specified at most one update per animation frame. Real LLM streams are about one token per frame, so per-frame coalescing may not reduce parse count, and S0 confirmed it ([results](../02-benchmarks.md#phase-2-streaming-spike-s0)). At 20-character chunks (487 flushes with no window): no window 11.3×, 16 ms 11.3×, 33 ms 6.14× (mean/max lag 16.1/32.5 ms), 50 ms 4.36× (24.1/48.7 ms), 100 ms 2.72× (48.2/96.7 ms), 200 ms 1.84× (96.3/192.7 ms). Each flush costs about 0.37 ms in Node, far below a frame, so cost-adaptive throttling never engaged.
- **Decision:** the default depends on the platform, and an explicit window overrides it.
  - **iOS and Android:** one flush per animation frame (`requestAnimationFrame`). There is no leading flush: the first chunk after an idle period waits for the next frame.
  - **Web:** a fixed window of **16 ms** on a timer: a leading flush on the first chunk, then at most one flush per window, with a trailing flush at the end of a window that buffered anything, so the last chunk is never left unflushed.
  - **`flushIntervalMs` given:** that window on a timer, on every platform. This is the escape hatch for anyone who wants timer batching on a device.
  - Where `requestAnimationFrame` does not exist (Node, SSR, some test environments) the frame schedule falls back to a 16 ms timer. The scheduler stays React-free; the hook picks the default (`Platform.OS`).
  - Cost-adaptive throttling stays deferred. The revisit criterion ("flush p90 above one frame") did not trigger: on the S25 FE release build the flush p90 was 2.4 to 5.6 ms for every window up to 50 ms, and at most 12.3 ms at the 100 ms window, against a 16.7 ms frame. A single flush occasionally costs 25 to 54 ms in every configuration (max), which accounts for most of the frame-gap maximum.
- **Evidence** (full tables in [02-benchmarks](../02-benchmarks.md#phase-2-scheduler-s2); `bench/results/scheduler-*`):

  | Where | What it showed |
  |---|---|
  | Node `--jitless` (simulated 60 Hz frames, F2, 20-character chunks at 1250 chars/s) | `raf` flushes 467 times against 157 for `timeout@50`, about 2.7× the total cost (18.4× against 6.7× one full parse), for a lower, bounded latency (p50 8 ms, max 17 ms, against p50 24 ms, max 49 ms). Frames are simulated and React commit is not included, so this is indicative only. |
  | S25 FE, Expo Go (dev build) | Misleading. `timeout@50` dropped 8 to 14% of frames against 1.6 to 2.1% for `raf`; on the release build both drop 2 to 3%. Dev-mode overhead made the larger `timeout` commits miss frames. Not used for the decision. |
  | S25 FE, Hermes release, F2 | Dropped frames 1.6 to 3.3% for every schedule, so frame health does not separate them. Append-to-commit latency p50 / p90: `timeout@16` 22 / 36 ms, `@33` 34 / 51 ms, `@50` 43 / 64 ms, `@100` 76 / 116 ms, `raf` 15 / 21 ms. Flush cost sum over a 7.9 s stream: 571, 511, 463 and 436 ms for the four windows, 684 ms for `raf` (about 1.5× `timeout@50`). |
  | Web, headless Chromium 156, 4× CPU throttle, minified export, F2 | A flush costs under 1 ms at p90, so the schedule changes latency and commit count, not frame health. Latency p50 / p90: `timeout@16` 9 / 16 ms, `@33` 17 / 25 ms, `@50` 23 / 42 ms, `@100` 50 / 87 ms, `raf` 13 / 17 ms. Dropped frames 0 to 2.4%. |
  | Web, hidden tab (headed, one run each) | `raf` still finished and the document was correct, but took 27.1 s against 7.8 s in the foreground, with a longest gap between flushes of 6.5 s. `timeout@50` took 7.8 s with no stall. A single run each, and some of the stall may come from tab-switch timing. |

- **Rejected alternatives:**
  - **`timeout@33` everywhere** (simplest; about 34 ms latency on the device). It works on every platform, but gives up about 19 ms of latency on iOS and Android, where `raf` has no known downside, for no gain over the split.
  - **Visibility hybrid** (`raf` while visible, a timer while hidden). It needs a visibility signal on every platform (`document.visibilityState` on the web, `AppState` on native) and re-scheduling on every change. The only problem it fixes is a hidden web tab, which the web default already avoids, and on native the OS suspends frames and timers in the background anyway.
  - **Plain `raf` everywhere.** A hidden browser tab stalls it (27 s instead of 8 s), which matters for a chat answer that keeps arriving while the user is in another tab.
  - **A 50 ms window as the default** (this decision's earlier proposal). On web it cuts the flush count to about a third of 16 ms's (147 against 468) at the price of about 14 ms more median latency, to save work that is already small, because a web flush costs under 1 ms.
- **Caveats:**
  - **Display refresh rate.** Midway through the F4d device runs the S25 FE's display dropped from 120 Hz to 60 Hz (frame-gap p50 about 16.7 ms instead of about 8.5 ms, about half the frame samples, about half the `raf` flushes). Those four runs are excluded from every comparison and flagged `display60Hz` in the saved JSON. The F2 runs were all at 120 Hz. It also means the `raf` flush rate follows the display's refresh rate (up to the chunk rate), so `raf` costs less CPU on a 60 Hz phone than the numbers above.
  - **Not measured (waived, [P2-8](#p2-8-iphone-run-and-f4c-deferred)):** an iPhone (none available; `raf` there runs on `CADisplayLink`, which is expected to behave but is untested), and iOS background and resume. **Measured since (2026-11-06, S25 FE, Android 17, Hermes release; [results](../02-benchmarks.md#native-background-and-resume-s25-fe)):** a backgrounded native app keeps its buffered text and flushes it after resume. There is no `AppState` handling in `src/stream/scheduler.ts` or `useMarkdownStream.ts` (only the suspend and resume used for StrictMode), and none is needed: on Android `JavaTimerManager.onHostPause` freezes both `setTimeout` and `requestAnimationFrame` while the activity is paused, so the scheduler freezes with the host. No crash, no lost or duplicated text, final document equal to `parse(full)` in all 20 runs (JS steady and catch-up producers, a native-source producer, 3 s and 15 s backgrounds, timer 50 ms and `raf`, screen off and on four times). The first commit after resume came 10 to 59 ms later as one flush of the buffered text, with 1 to 5 frames over 20 ms (largest 21 to 47 ms), the same range as the foreground controls (largest frame gap 37 to 40 ms). `done()` called while backgrounded commits 175 to 286 ms later (17 to 36 ms in the foreground), and `done()` after resume works. **No scheduler change is needed.** Not tested: a producer that stalls in the background, a real network stream, iOS.
- **S5 React hook numbers (2026-11-06, S25 FE, Hermes release, 120 Hz, 20 runs each, 0 rejected; [results](../02-benchmarks.md#react-hook-50-ms-timer-against-raf)):** a 50 ms timer against `raf` through `useMarkdownStream`. `F4a`: 129 against 465 commits, `streamRender` 1344 / 1484 ms against 2268 / 2351 ms (p50 / p90), render p90 15.5 against 8.3 ms, janky frames (`gfxinfo`) 114 of 162 (70.2%) against 221 of 486 (45.6%), JS gaps over 20 ms 22 against 14, `done` to commit 31.8 against 20.9 ms. `F4b`: 13 against 45 commits, `streamRender` 126.7 against 261.9 ms, render p90 14.6 against 9.7 ms. `F4d`: 75 against 276 commits, `streamRender` 366.5 against 709.1 ms, render p90 6.8 against 3.9 ms. The timer does less total work but each commit is about twice as expensive, and `raf` has lower latency to the final commit and a lower janky-frame percentage at 120 Hz. This does not change the accepted default; it is input to the P2-1 choice of window.
- **Consequences:** Updates `05 · Rendering`, [hook-and-scheduler](./hook-and-scheduler.md#scheduler) and [02-benchmarks](../02-benchmarks.md#phase-2-scheduler-s2). The 5× `F4a` bar of [P2-1](#p2-1-exit-criterion-wording-and-the-f4-fixture) assumed a 50 ms window; with a 16 ms or per-frame schedule the `streamCost` multiple is higher (about 18× in Node for `raf`), so P2-1 must be re-read in that light at S5 (done: P2-1 accepted 2026-11-06 at an explicit 50 ms window), with the device cost in absolute milliseconds (the sum of flush costs over the stream was 436 to 684 ms for 7.9 s of F2 on the S25 FE). [smoothing](./smoothing.md) is about what the open block shows, not about flush cadence, and does not say whether text appears per frame.

## P2-5: Open fence fast path

- **Status:** Accepted (2026-11-05). Ships in Phase 2: implemented in S1 and the equivalence harness matches a full parse with it on and off (1400 tests, no allowlist entries). First device measurement taken in S2 (see **Device result** below): it halves flush cost on the code-heavy stream and changes nothing else. The iOS check (waived, [P2-8](#p2-8-iphone-run-and-f4c-deferred)) can only turn it off (`FENCE_FAST_PATH_DEFAULT` in `src/stream/createMarkdownStream.ts`), not change the equivalence requirement.
- **Date:** 2026-11-05
- **Context:** 05 describes appending text to an open fenced block without a re-parse ([stream-algorithm](./stream-algorithm.md#open-fenced-code-fast-path)). On F2 the case for it is weak: fenced code is 4.6% of tail flush cost at 20-character chunks and 13.4% at 195, tables are 33.6% and 17.2%, lists 23.8% and 18.7%, and the fast path skipped 78 of 487 flushes and saved about 1.5% of total cost (10.5× against 10.7×). A code-heavy stream is different ([results](../02-benchmarks.md#code-heavy-fixture)): on `bench/fixtures/code-heavy.md` (5.6 KB, one ~4.5 KB fence) the open fence is 89.0% of flush cost at 20 characters and 86.2% at 195. The fast path takes `streamCost` from 56.9× to 7.24× at 20 characters (249 of 281 flushes skipped) and from 6.79× to 1.63× at 195, with no added lag, while a 50 ms window alone still leaves 19.1×. The multiples are inflated by a tiny full-parse denominator: absolute cost is 37 ms against 4.7 ms for the whole stream, about 100 ms against 13 ms on Hermes. The spike's fast path only appended text and did not build a document, so it showed no equivalence with a full parse.
- **Decision (proposed):** ship the open-fence fast path in Phase 2, to be confirmed with device measurements (together with [P2-1](#p2-1-exit-criterion-wording-and-the-f4-fixture) and [P2-4](#p2-4-coalescing-policy), on Hermes on a real device at S5) and an equivalence test. It ships only if the equivalence harness shows it matches a full parse.
- **Device result (2026-11-05, S25 FE, Hermes release build, 120 Hz, `F4d`: 5619 characters in 20-character chunks every 16 ms, 281 chunks):** with the fast path on, the sum of flush costs over the stream is about half of what it is with it off.

  | Schedule | Fast path on | Fast path off |
  |---|---|---|
  | `timeout@50` (3 runs each) | 108 ms (77 flushes; p90 5.2 ms) | 236 ms (76 flushes; p90 8.8 ms) |
  | `raf` (the two final runs at 120 Hz in each state) | 171 ms (169, 172) | 354 ms (355, 353) |

  Append-to-commit latency and dropped frames did not change with it (`timeout@50` p50 41 ms on against 39 ms off, dropped 1.4% against 0.8%; `raf` dropped 0 of about 500 frames in the clean runs). The saving is small in absolute terms, about 130 to 180 ms over a 4.5 s stream, so the ratio is the signal. `F4d`'s bar stays TBD as above, and should be absolute cost, not a multiple of a 13 ms full parse. Excluded: the four `raf` runs taken while the display had dropped to 60 Hz (see [P2-4](#p2-4-coalescing-policy)). Data: `bench/results/scheduler-device-s25fe-release-f4d-2026-11-05.json`. The fast path is on by default and stays on.
- **Consequences:** the equivalence harness must cover it ([testing-harness](./testing-harness.md#targeted-cases)): randomized chunking, including fences split mid-marker, closing-fence candidates, indented fences, and fences inside lists and quotes falling back to the normal path. The [stream-algorithm](./stream-algorithm.md#open-fenced-code-fast-path) section is active again. Tables and lists remain the next place to look for open-block cost. Whether a ratio is the right bar for code-heavy streams is a P2-1 question (`F4d`, [benchmark-protocol](./benchmark-protocol.md#f4)).

## P2-6: `hide-incomplete` semantics

- **Status:** Accepted (2026-11-05), implemented in S3.
- **Date:** 2026-11-05
- **Context:** 05 only says "buffers trailing unclosed inline markers". Two readings: hide the dangling marker, or auto-close it.
- **Decision:** hide, applied to the open block's view only ([smoothing](./smoothing.md)). No extra one-word lag; nested runs are cut at the earliest unclosed opener ([details](./smoothing.md#semantics)). The stream core keeps its exact table for resuming, and only the table it returns is the smoothed view: the open block is parsed again from the smoothed text, and only when smoothing changed the text (otherwise the returned table is the exact one). `done()` and `reset()` return the exact parse.
- **Consequences:** none on `source` or on the final document. Costs a second parse of the open block on flushes where a fragment is hidden. Smoothing does not give per-frame visual updates between flushes (the open point in [P2-4](#p2-4-coalescing-policy)): it changes what a flush shows, not when.

## P2-7: Where the Phase 1 carry-over lives

- **Status:** Accepted (2026-11-06)
- **Date:** 2026-11-06
- **Context:** [P1-25](../phase-1/decisions.md#p1-25-the--5-parse-plus-first-render-exit-criterion-is-waived-for-phase-1) waived the ≥ 5× parse-plus-first-render criterion (F3: 1.0× on the S25 FE, 1.08× on web, [results](../02-benchmarks.md#device-results-m7)) and carried five items into Phase 2 "as an open performance item".   - **The 5× target is restated at the v1.0 gate**, against the item 1 baseline, instead of the current F3 comparison that cannot reach it. Whether it stays 5× is decided with that data, as a new decision, not now.
- **Consequences:**
